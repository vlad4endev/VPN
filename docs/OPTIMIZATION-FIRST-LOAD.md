# Оптимизация первой загрузки — отчёт

## 1. Список внесённых изменений

### Уже было сделано ранее (подтверждено)
- **Блокирующие операции до `app.listen`** — убраны: инициализация Firebase выполняется в `setImmediate` после `listen`, первый ответ не ждёт БД.
- **Агрегирующий endpoint `/api/init`** — реализован: один запрос возвращает `{ user, tariffs }` с минимальными полями; Bearer-авторизация.
- **Gzip compression** — включён в `n8n-webhook-proxy.js` (middleware `compression()`).
- **Кэширование** — Redis для настроек (`getSettingsCached`); in-memory кэш для `/api/init` по uid (TTL 60 с); кэш результата `verifyIdToken` по хешу токена (TTL 2 мин).
- **Оптимизация запросов к БД** — параллельные запросы (`Promise.all`) в resolve-login, send-reminders, getTelegramToken; Firestore-запрос напоминаний по `expiresAt` с чанками; для `/api/init` добавлен `tariffsRef.limit(500)`.
- **Очередь для Telegram** — при наличии `REDIS_URL`: BullMQ-очередь для webhook, ответ 200 сразу; in-memory лимитер при отсутствии Redis.
- **Graceful shutdown** — закрытие BullMQ worker/queue, Redis, `server.close()`, принудительный выход через 15 с.
- **Логирование времени ответа** — middleware логирует длительность запроса (вкл. через `LOG_REQUEST_MS` или в dev).
- **Firebase при авторизации** — меньше вызовов: кэш `verifyIdToken`, `ensureAdminByUid` без повторной верификации, кэш ответа `/api/init`.

### Изменения в этой сессии
- **Cache-Control для эндпоинтов**
  - `GET /health` — `Cache-Control: no-store, no-cache, must-revalidate` (health-check не кэшируется прокси/LB).
  - `GET /api/push-vapid-public` — `Cache-Control: public, max-age=3600` (клиент может кэшировать ключ 1 ч).
- **Keep-alive** — после `app.listen` заданы `server.keepAliveTimeout = 65000`, `server.headersTimeout = 66000` (снижение повторных TCP handshake при частых запросах).
- **Redis для `/api/init`** — при наличии `REDIS_URL`: перед обращением к Firestore проверяется Redis-ключ `init:{uid}`; после загрузки из БД ответ пишется в Redis с TTL 60 с. Порядок: in-memory → Redis → Firestore.
- **Compression в proxy-server и payment-server** — добавлен `app.use(compression())` в оба сервера для сжатия ответов.
- **Лимит тарифов в `/api/init`** — `tariffsRef.limit(500)` для ограничения объёма чтения из Firestore.

### Статика и CDN (без изменения кода в этой сессии)
- **proxy-server.js** — для статики из `dist` уже задано `maxAge: '1y'` в production.
- **proxy-server.optimized.js** — для статики задан заголовок `Cache-Control: public, max-age=31536000, immutable`.
- Рекомендация: отдавать статику через CDN или nginx с теми же заголовками кэширования.

### Не менялось (по решению ранее)
- **Lazy loading тяжёлых модулей** — не внедрялся (риск поломки при динамическом `import()` в путях с высокой нагрузкой).
- **NocoDB import** — цикл импорта не трогали из-за сложной общей логики.
- **Bundle size / неиспользуемые зависимости** — отдельный аудит фронта и сервера рекомендуется выполнить вручную (например, `npx depcheck`, анализ бандла Vite).

## 2. Ожидаемое сокращение времени первого ответа

- **TTFB первого запроса (до listen)**  
  Раньше: мог блокироваться инициализацией Firebase.  
  Сейчас: сервер сразу отвечает на запросы; Firebase поднимается асинхронно. Ожидаемое улучшение: **сотни миллисекунд – несколько секунд** на холодном старте (зависит от окружения).

- **Повторные запросы `/api/init` (один и тот же пользователь)**  
  In-memory кэш (60 с): ответ без Firestore.  
  Redis-кэш (при включённом Redis): тот же эффект для нескольких инстансов и после рестарта.  
  Ожидаемое сокращение: **~100–300 мс** на запрос при попадании в кэш (вместо 1–2 обращений к Firestore).

- **Размер ответов**  
  Gzip на всех трёх серверах (n8n-webhook-proxy, proxy-server, payment-server) уменьшает объём по сети для JSON и статики. Типичное сокращение: **50–70%** размера текстовых ответов.

- **Health-check для cold start**  
  `GET /health` без БД и с `Cache-Control: no-store` позволяет балансировщику быстро проверять готовность инстанса без кэширования устаревшего ответа.

- **Итог**  
  Первый ответ сервиса после деплоя/рестарта должен приходить **сразу после listen** (десятки миллисекунд для `/health` и лёгких маршрутов). Время до «полной готовности» (Firebase, очереди) по-прежнему занимает 1–3 с в фоне, но не блокирует TTFB.

## 3. Потенциальные точки масштабирования

- **Горизонтальное масштабирование API**  
  - Один инстанс: in-memory кэши (init, token, settings) достаточны.  
  - Несколько инстансов: Redis обязателен для единого кэша (`/api/init`, настройки, при необходимости — сессии). Уже заложено: при `REDIS_URL` используется Redis для init и настроек.

- **Telegram webhook**  
  При высокой частоте обновлений: BullMQ + Redis (уже реализовано). При дальнейшем росте — вынести воркер в отдельный процесс/сервис и масштабировать только воркеры.

- **Firestore**  
  Уже: параллельные запросы, лимиты, кэширование. Дальше: композитные индексы под частые запросы (напоминания, логины), при необходимости — шардирование коллекций или выделение «горячих» данных.

- **Статика**  
  Вынести раздачу статики на CDN или отдельный edge-сервер; оставить API только в n8n-webhook-proxy — уменьшится нагрузка на Node и улучшится TTFB для статики по географии.

- **Health-check**  
  Использовать `GET /health` в проверках готовности (K8s readiness/liveness, AWS Target Group и т.п.) для быстрого снятия с балансировки при остановке и возврата в пул после listen.

## 4. Рекомендации для high-load режима

1. **Обязательно**  
   - Включить `REDIS_URL` для кэша init/settings и очереди Telegram.  
   - Настроить балансировщик на `GET /health` без кэширования.  
   - Оставить включённым rate limiting и compression на всех серверах.

2. **Желательно**  
   - Вынести статику на CDN/nginx с долгим кэшем (`Cache-Control: public, max-age=31536000, immutable` для хешированных файлов).  
   - Мониторить время ответа эндпоинтов (уже есть middleware) и метрики Firestore/Redis.  
   - При росте нагрузки на Telegram — отдельный сервис-воркер для BullMQ.

3. **Опционально**  
   - Аудит зависимостей и размера бандла (front + server).  
   - Lazy load тяжёлых модулей только после профилирования и выбора безопасных маршрутов.  
   - Рассмотреть отдельный пул соединений к Firestore и лимиты на количество одновременных запросов к БД.

Бизнес-логика в результате оптимизаций не менялась; фокус — на быстром первом открытии, минимальном TTFB и плавной загрузке.
