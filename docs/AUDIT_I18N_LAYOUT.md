# Аудит: i18n (ключи вместо переводов), верстка, стабилизация

## 1. Диагностика

### 1.1 Структура проекта
- **Frontend:** Vite + React 18, точка входа `index.html` → `src/app/main.jsx` → `App.jsx`.
- **Роутинг:** без React Router — навигация по состоянию `currentView` и `localStorage` (`vpn_current_view`). Компоненты `PublicRoute`/`ProtectedRoute` не используются.
- **Состояние:** локальный state в `App.jsx`, React Query, Firebase Auth, zustand (uiStore для вкладок админки/кабинета).
- **i18n:** один namespace `translation`, ресурсы подгружаются статически из `src/i18n/locales/*.json` (ru, en, hi, ar, tg, uz, kk, ky, zh). Инициализация в `src/i18n/index.js`, детектор: localStorage → navigator.
- **Telegram initData:** в `index.html` — скрипт копирует `Telegram.WebApp.initData` в `window.__TELEGRAM_INIT_DATA`, перехват `fetch` для заголовка `X-Telegram-InitData`. В `App.jsx` — `getTmaInitData()`, авто-вход POST `/api/telegram/auth`, `hasTmaInitData` → `isTelegramApp`.
- **Сборка:** Vite 7, Tailwind 3, PostCSS. Сборка: `vite build`, статика в `dist/`.

### 1.2 Что проверено
- Во всех 9 локалях есть секция `auth` с ключами `login`, `register` и остальными.
- Рендер приложения выполняется после `i18nReady` (`main.jsx`: `i18nReady.then(renderApp)`). При ошибке инициализации i18n вызывается `renderApp()` в `catch` — приложение рендерится с неинициализированным или частично инициализированным i18n, и `t()` возвращает ключи.
- В `LoginForm` есть fallback через `labelT(t, key, forceFallbackLabels)` и `AUTH_FALLBACKS`, но только для части ключей и только при `isTelegramApp || isMobileView`. В браузере без Telegram при падении i18n ключи будут видны.
- В `react-i18next` по умолчанию `useSuspense: true`. Ожидание готовности через `i18nReady` перед первым рендером должно исключать подвешивание, но при сбое инициализации возможны краевые случаи.
- Детектор языка не учитывает `Telegram.WebApp.initDataUnsafe.language_code` — язык интерфейса Telegram не подставляется при первом заходе в Mini App.
- Верстка: глобальные стили в `src/app/index.css`, Tailwind content: `index.html`, `src/**/*.{js,jsx,ts,tsx}`. Есть safe-area, clamp, контейнеры. Возможные причины «кривой» верстки: отсутствие явного контейнера для `#root`, конфликт классов или переполнение на мобильных.

## 2. Причины проблем

### 2.1 Почему показываются ключи (auth.login, auth.register и т.д.)
1. **Сбой инициализации i18n:** при ошибке в `i18n.init()` или в `.then()` после init (например, при `applySystemLanguageIfNeeded` / `changeLanguage`) промис `i18nReady` отклоняется, в `main.jsx` срабатывает `catch`, приложение всё равно рендерится. В этот момент i18n может быть не готов — `t()` возвращает ключ.
2. **Нет явного отключения Suspense:** при нестандартном порядке загрузки (например, в WebView Telegram) теоретически возможны ситуации, когда компонент рендерится до полной готовности i18n.
3. **Язык вне списка:** если детектор вернёт код, которого нет в `supportedLngs`, и цепочка fallback не сработает, i18next может отдавать ключ. Явный массив `fallbackLng` повышает предсказуемость.

### 2.2 Почему переводы могут не подгружаться
- Ресурсы подключены статически (import JSON), при успешной загрузке бандла они есть. Проблема не в «подгрузке», а в **готовности экземпляра i18n** и **корректном выборе языка** (в т.ч. fallback).
- Отсутствие детектора по Telegram: первый язык берётся из localStorage или navigator; язык приложения в Telegram не учитывается.

### 2.3 Стили / верстка
- В проекте один глобальный CSS, Tailwind и утилиты (container-responsive, safe-area, touch-target). Конфликтов с другими фреймворками нет.
- Возможные источники «кривого» интерфейса: недостаточная обвязка `#root` (min-height, overflow), разные значения высоты (100vh vs 100dvh) в разных местах, или элементы с фиксированной шириной без `max-width: 100%`. Рекомендуется явно задать для `#root` минимальную высоту и управление overflow.

### 2.4 SSR / CSR и hydration
- Приложение полностью клиентское (CSR), SSR нет. Ошибок гидрации из-за i18n не ожидается; важно не рендерить до готовности i18n (что уже делается через `i18nReady`).

## 3. План безопасного исправления

### Этап 1 (минимальные изменения, без смены API)
1. **i18n**
   - Включить `react.useSuspense: false` в конфиге i18n.
   - Задать явный `fallbackLng: ['ru', 'en']`.
   - Сделать инициализацию устойчивой к ошибкам: обернуть логику в try/catch, в случае ошибки всё равно разрешать `i18nReady` (i18n остаётся в рабочем состоянии с дефолтным языком).
   - Добавить детектор языка из Telegram WebApp (`language_code`) и вставить его в начало порядка детекции (например, после localStorage).
2. **Точка входа**
   - Оставить текущую логику: рендер после `i18nReady`; в `catch` по-прежнему вызывать `renderApp()`, но после правок i18n сбой будет обрабатываться внутри init и промис не будет отклоняться без необходимости.
3. **Верстка**
   - В глобальных стилях задать для `#root` минимальную высоту и overflow, чтобы layout не «ломился» на мобильных.

### Этап 2 (по необходимости)
- Расширить fallback-обвязку для критичных ключей в других компонентах (по аналогии с `LoginForm`), если после этапа 1 останутся кейсы с ключами.
- Проверить использование `max-w-content` / `container-responsive` во всех основных экранах.

### Что не менять
- API (backend, контракты запросов/ответов).
- Логику авторизации через Telegram initData и проверку на бэкенде.
- Структуру роутинга (state + localStorage).
- Полную перезапись проекта или массовую замену компонентов.

## 4. Конкретные изменения в коде

### 4.1 `src/i18n/index.js`
- В `init()` добавить:
  - `react: { useSuspense: false }`
  - `fallbackLng: ['ru', 'en']`
- Перед вызовом `i18n.use(LanguageDetector)` зарегистрировать кастомный детектор для Telegram (см. ниже).
- В `.then()` после init обернуть вызовы `applySystemLanguageIfNeeded` и `changeLanguage` в try/catch; при ошибке логировать и не отклонять промис.
- Весь блок инициализации (включая цепочку `.use().init()`) обернуть в try/catch: при любой ошибке — логирование, при необходимости принудительно выставить язык `ru` и всё равно разрешить промис, чтобы приложение не рендерилось с «битым» i18n.

### 4.2 Детектор языка Telegram
- В `detectSystemLanguage.js` добавить функцию `getTelegramLanguageCode()`: читать `window.Telegram?.WebApp?.initDataUnsafe?.language_code`, маппить на один из `supportedLngs` (ru, en, ...), иначе возвращать `null`.
- В `src/i18n/index.js` добавить кастомный детектор i18next (order: `localStorage` → `telegram` → `navigator`), где `telegram` — результат `getTelegramLanguageCode()`.

### 4.3 `src/app/index.css`
- Для `#root`: задать `min-height: 100dvh` (с fallback на `100vh`), `width: 100%`, `overflow-x: hidden`, при необходимости `display: flex; flex-direction: column` для sticky footer.

### 4.4 Конфиг
- Никаких изменений в `vite.config.js` или API не требуется. Только опции i18n и глобальные стили.

## 5. Чеклист регрессионного тестирования

- [ ] **Вход/регистрация (браузер):** форма входа и регистрации — везде переводы, не ключи (auth.login, auth.register и др.).
- [ ] **Вход/регистрация (Telegram Mini App):** то же в WebView; язык интерфейса Telegram при первом заходе подхватывается (если добавлен детектор).
- [ ] **Welcome:** все блоки (hero, преимущества, тарифы, отзывы) — переводы, не ключи.
- [ ] **Сайдбар и футер:** пункты меню и ссылки футера — переводы; при отсутствии ключа — дефолтные строки (как в Footer с `t('footer.showFooter', 'Подвал')`).
- [ ] **Личный кабинет:** статусы, кнопки, модалки (ключ, тариф, оплата) — переводы.
- [ ] **Админка:** заголовки и навигация — переводы.
- [ ] **Переключение языка:** смена языка в переключателе обновляет интерфейс без перезагрузки; выбранный язык сохраняется в localStorage и применяется при следующем визите.
- [ ] **RTL:** при выборе арабского (ar) у `document.documentElement` выставляется `dir="rtl"`.
- [ ] **Верстка:** главная, форма входа, кабинет, админка — без горизонтального скролла на мобильном; контент не обрезается; safe-area учитывается на устройствах с вырезами.
- [ ] **Авторизация:** вход по email/паролю, вход через Telegram (Mini App и виджет), авто-вход по initData — без изменений в поведении.
- [ ] **API:** запросы к `/api/telegram/auth` и остальным эндпоинтам — без изменений в теле/заголовках.

## 6. Рекомендации по стабилизации проекта

1. **Мониторинг i18n:** в dev логировать предупреждения i18next при отсутствующих ключах; при необходимости включить `saveMissing` только для разработки.
2. **Единый эталон ключей:** держать `ru.json` (или `en.json`) эталоном и периодически сверять ключи в остальных локалях (как в I18N_CHECKLIST.md).
3. **Критичные экраны:** для экранов входа и приветствия по желанию оставить локальные fallback-объекты (как AUTH_FALLBACKS в LoginForm), чтобы даже при сбое i18n пользователь видел осмысленный текст.
4. **Верстка:** использовать один контейнер (например, `container-responsive` или обёртка с `max-w-content`) для всех основных страниц; для полноэкранных блоков — `min-h-screen` / `min-h-[100dvh]` и единый подход к safe-area.
5. **Сборка:** перед релизом запускать `vite build` и проверять открытие приложения из `dist/` в браузере и в Telegram WebView.

## 7. Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| После включения `useSuspense: false` где-то предполагалось поведение Suspense | Низкая | Рендер уже идёт после `i18nReady`; отключение лишь страхует краевые случаи. |
| Детектор Telegram подставит язык, который пользователь не выбирал | Низкая | Детектор срабатывает только при отсутствии сохранённого выбора (localStorage); при следующем визите приоритет у localStorage. |
| Изменение `fallbackLng` повлияет на уже сохранённый язык | Нет | `fallbackLng` используется только при отсутствии перевода для выбранного языка. |
| Правки в CSS сломают существующие экраны | Низкая | Меняются только глобальные стили для `#root` (минимальная высота и overflow). |
